# PDF智能问答系统 — 开发对话记录（阶段一：单提示词生成）

## 1. 需求理解

根据实验文档和提示词要求，需要构建一个基于 RAG 的复杂 PDF 文档智能问答系统。核心要求：

- 使用 LlamaIndex 框架对 PDF 进行向量化
- 使用 Milvus Lite 存储向量数据
- 使用 DeepSeek 作为大模型
- 使用 Streamlit 搭建前端
- PDF 解析需同时处理文本、表格、图表
- 文本/表格/图片建立独立索引
- 前端能检测 API 和数据库连接状态，支持修改 API Key 和上传 PDF

源文档是一份 23 页的金融研报，包含市场分析文本、指数估值表格、行业 PE 对比图表等混合内容。

## 2. 初始架构设计

创建了两阶段的项目结构：

- 根目录存放环境相关文件（.env、requirements.txt、setup 脚本）
- PromptVersion 目录存放阶段一的生成代码（build_kb.py、app.py、prompt.txt、README.md）

build_kb.py 负责：PDF 解析 → 向量化 → Milvus 存储
app.py 负责：Streamlit 前端 → 检索 → DeepSeek 问答

技术选型：
- PDF 解析：最初使用 pdfplumber + PyMuPDF 联合解析
- 图片 OCR：EasyOCR（中英文混合识别）
- 向量化：BAAI/bge-small-zh-v1.5（512 维，中文金融文本优化）
- 向量存储：Milvus Lite（嵌入式，文本/表格/图片三个独立集合）
- 大模型：DeepSeek-Chat（OpenAI 兼容 API）

## 3. 遇到的问题与解决过程

### 问题一：requirements.txt 安装失败

运行 pip install -r requirements.txt 时报 UnicodeDecodeError，原因是 Windows 的 pip 用 GBK 解码 UTF-8 文件，中文注释中的特殊字符（如 em-dash "—"）导致解码失败。

解决：将 requirements.txt 中所有中文注释替换为 ASCII 英文注释。

### 问题二：Milvus 集合 released 状态

构建知识库后，Streamlit 前端检索时提示"未检索到相关内容"。诊断发现三个集合（text:23 条, table:6 条, image:59 条）数据都在，但处于 released 状态。

原因：Milvus Lite 在连接断开后，集合会自动释放内存。需要在每次连接后调用 load_collection() 将数据加载到内存才能搜索。

解决：在 build_kb.py 的 insert 方法中，插入数据后立即调用 load_collection()。在 app.py 的 get_milvus_client 方法中，连接后自动加载所有已有集合。

### 问题三：pdfplumber 中文编码乱码

这是最关键的问题。用 4 道样本题目测试时全部答错，检查检索结果发现 pdfplumber 提取的文本全是乱码。

原因：pdfplumber 对该 PDF 的中文内嵌字体编码支持有问题，提取出的文本不可读。

解决：将文本提取从 pdfplumber 全面切换为 PyMuPDF（fitz）。PyMuPDF 的 page.get_text() 方法对该 PDF 的中文编码兼容性完美，提取出的文字完全可读。

### 问题四：PyMuPDF find_tables 同样乱码

仅切换文本提取后，表格提取仍使用 PyMuPDF 的 find_tables() 方法，但发现该方法对该 PDF 的表格提取也存在编码问题。

解决：去掉独立的表格提取。因为 PyMuPDF 的 page.get_text() 已经将表格内容作为文本包含在页面输出中，表格数据不会丢失。精简为两个集合：text_collection 和 image_collection。

### 问题五：整页文本搜索精度低

最初将每页 PDF 作为一整段文本向量化存储（23 页 = 23 条向量）。但由于每段文本太长（1000+ 字符），向量语义被稀释，导致相似度搜索精度很低。例如"沪深300上涨家数占比"的公式定义就在第 8 页，但相似度只有 0.19，被大量无关内容挤到了检索结果的后面。

解决：引入 LlamaIndex 的 SentenceSplitter 对文本进行分块（chunk_size=512, overlap=50），23 页被切分为 67 个文本块。每个块的含义更集中，检索精度大幅提升。

### 问题六：页面页眉页脚噪声

每页 PDF 开头都有重复的"敬请阅读最后一页特别声明"、"-N- 证券研究报告 金融工程"等页眉页脚。这些文本在分块后仍会出现在多个块中，既浪费向量空间，又稀释了核心内容的语义。

解决：在提取文本后清洗掉重复的页眉页脚行（包括页码标记、免责声明、固定栏目名等）。

### 问题七：图片 OCR 向量分数系统性偏高

最后一个关键问题是：image_collection 的 59 条图片 OCR 向量在相似度搜索时分数系统性高于 text_collection 的 67 条文本块。导致混合排序后，LLM 收到的上下文前几条全是不精确的 OCR 图片描述，准确的文本内容反而被挤到了后面。

原因：OCR 提取的文本碎片化程度高、关键词密度大（如行业名、数值密集排列），与查询语句的向量相似度被高估。

解决：将"按分数混合排序"改为"均衡采样策略"。文本集合取 top_k（8 条），图片集合只取 top_k//2（4 条），合并时文本结果排在前面。这样确保 LLM 优先看到准确的文本内容，图片 OCR 作为补充。

## 4. 最终测试结果

用实验文档指定的 4 道样本题目进行测试，全部正确：

1. "截至2023年7月7日，从宽基指数来看，创业板指处于估值分位数的什么等级？" → 答案正确："安全"等级。

2. "沪深300上涨家数占比情绪指标的计算方法是什么？" → 答案正确：完整给出了"沪深300指数N日上涨家数占比 = 沪深300指数成分股过去N日收益大于0的个股数占比"的公式定义及参数设置（N=230，N1=50，N2=35）。

3. "从宽基指数表现上看，沪深300的开盘价是多少？" → 答案正确：3853.29。

4. "在中信一级行业指数估值中，有色金属的PE（TTM）值是多少？" → 答案正确：14.84。

## 5. 关键技术要点总结

- PDF 中文编码兼容性：PyMuPDF（fitz）比 pdfplumber 对中文 PDF 的支持好得多，是处理中文 PDF 的首选工具。
- 文本分块至关重要：整页文本直接向量化会导致语义稀释，必须切分为 500 字符左右的小块才能保证检索精度。
- 噪声清洗：PDF 页眉页脚、页码、免责声明等重复内容需要清洗，否则会显著降低向量质量。
- Milvus Lite 需手动 load：每次新连接都需要调用 load_collection() 将集合加载到内存。
- 多集合检索需均衡：不同类型内容的向量分数不可直接比较，需要用比例控制而非简单按分排序。
