# AI开发技术实验3：基于RAG的复杂PDF文档智能问答系统

---

## 前言：RAG 技术背景

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种结合信息检索与文本生成的 AI 架构。它的核心思想是：大语言模型（LLM）在回答用户问题之前，先从外部知识库中检索相关文档片段，将这些片段作为"参考资料"一起送入 LLM，从而让模型基于真实数据作答，减少幻觉。

本实验构建的 RAG 系统工作流程如下：

```
PDF 文档 → 解析提取文本/表格/图片 → 文本分块 → 向量化(Embedding) → 存入向量数据库(Milvus)
                                                                            ↓
用户提问 → 问题向量化 → 向量相似度检索 → 获取Top-K相关片段 → 组装Prompt → LLM生成回答
```

![RAG技术流程图](实验记录(图片)/RAG流程图.png)

核心组件分工：
- **PDF 解析器**：从 PDF 中提取可读的文本、识别图片中的文字（OCR）
- **嵌入模型**：将文本转换为固定维度的数学向量，语义相近的文本向量距离近
- **向量数据库**：存储和高效检索海量向量
- **大语言模型**：基于检索到的参考资料生成准确回答
- **前端界面**：提供用户交互入口

### 3.4 遇到的问题与解决

阶段一共遇到并解决了 **7个问题**，其中3个属于关键性技术问题。

---

**Issue #1：requirements.txt 中文编码导致pip安装失败**

- **现象**：`pip install -r requirements.txt` 报 `UnicodeDecodeError`
- **原因**：Windows 的 pip 使用 GBK 解码 UTF-8 文件，requirements.txt 中文注释中的特殊字符（em-dash "—"）导致解码失败
- **解决**：将 requirements.txt 中所有中文注释替换为 ASCII 英文注释

---

**Issue #2：Milvus 集合 released 状态**

- **现象**：构建知识库后，Streamlit 前端检索提示"未检索到相关内容"。检查发现三个集合数据都在，但处于 `released` 状态
- **原因**：Milvus Lite 在连接断开后，集合会自动释放内存。每次新连接后需要手动调用 `load_collection()` 将数据加载到内存才能搜索
- **解决**：在 `build_kb.py` 的 `insert` 方法中插入后立即调用 `load_collection()`；在 `app.py` 每次获取 Milvus 客户端时，自动加载所有已有集合

---

**Issue #3：pdfplumber 中文编码乱码**（关键问题）

- **现象**：用 4 道样本题目测试，全部答错。检查检索结果发现 pdfplumber 提取的文本全是乱码
- **原因**：pdfplumber 对该 PDF 的中文内嵌字体编码支持有问题
- **解决**：将文本提取全面从 pdfplumber 切换为 PyMuPDF（fitz）。`page.get_text("text")` 方法对该 PDF 的中文编码兼容性完美

---

**Issue #4：PyMuPDF find_tables() 同样乱码**

- **现象**：切换文本提取后，`find_tables()` 提取的表格仍存在编码问题
- **解决**：去掉独立的表格提取（`table_collection`）。因为 PyMuPDF 的 `page.get_text("text")` 已经将表格内容作为文本包含在页面输出中，表格数据不会丢失。精简为两个集合：`text_collection` 和 `image_collection`

---

**Issue #5：整页文本搜索精度低**（关键问题）

- **现象**：每页 PDF 作为一整段文本向量化（23页 = 23条向量），但每段文本 1000+ 字符，向量语义被稀释。"沪深300上涨家数占比"的公式定义在第8页，但相似度只有 0.19，被大量无关内容挤到检索结果后面
- **解决**：引入 LlamaIndex 的 `SentenceSplitter` 对文本分块（chunk_size=512, overlap=50）。23页被切分为 67 个文本块，每个块含义集中，检索精度大幅提升

---

**Issue #6：页面页眉页脚噪声**

- **现象**：每页重复出现"敬请阅读最后一页特别声明"、"-N- 证券研究报告 金融工程"等页眉页脚，分块后仍出现在多个块中，浪费向量空间并稀释核心内容语义
- **解决**：在文本提取后清洗重复噪声行（页码标记、免责声明、固定栏目名等）

---

**Issue #7：图片OCR向量分数系统性偏高**（关键问题）

- **现象**：image_collection 的 59 条图片 OCR 向量在相似度搜索时分数系统性高于 text_collection 的 67 条文本块。混合排序后，LLM 收到的上下文前几条全是不精确的 OCR 图片描述，准确的文本内容被挤到后面
- **原因**：OCR 提取的文本碎片化程度高、关键词密度大（行业名、数值密集排列），与查询语句的向量相似度被高估
- **解决**：将"按分数混合排序"改为"均衡采样策略"——文本集合取 top_k（8条），图片集合只取 top_k//2（4条），合并时文本结果排在前面。确保 LLM 优先看到准确的文本内容，图片 OCR 作为补充

---

### 3.5 初始方案 vs 最终方案

经过7个问题的迭代修正，技术方案发生了根本性变化：

| 组件 | 初始方案（Agent生成） | 最终方案（调试修正后） | 变更原因 |
|------|---------------------|---------------------|---------|
| PDF 文本提取 | pdfplumber | PyMuPDF (fitz) | Issue #3：pdfplumber 中文乱码 |
| 表格提取 | PyMuPDF find_tables() 独立集合 | 不单独提取，表格文本包含在 page.get_text() 中 | Issue #4：find_tables() 同样编码问题 |
| 向量集合 | 3个（text + table + image） | 2个（text + image） | Issue #4：表格集合冗余 |
| 文本存储粒度 | 每页整段（23条） | 分块存储（67条） | Issue #5：整页检索精度低 |
| 文本内容 | 含页眉页脚的原始文本 | 清洗噪声后的清洁文本 | Issue #6：噪声稀释语义 |
| 多集合检索排序 | 按向量分数混合排序 | 均衡采样（text:8 + image:4），文本优先 | Issue #7：图片OCR分数虚高 |

## 四、阶段二：Agent + 多Skill协同生成（SkillVersion）

### 4.1 设计思路

与阶段一"单提示词一次性生成"不同，阶段二采用以下策略：

1. **引入社区 Skill**：从社区 Skill 市场（skillsmp.com、claude-plugins.dev、anthropics/skills）中选取成熟的通用 Skill 作为架构指引，而非全部从零定义
2. **保留项目特有 Skill**：中文金融 PDF 的解析经验（PyMuPDF 编码处理、页眉页脚清洗）是项目特定的，保留为自定义 Skill
3. **分阶段驱动**：按 5 个阶段逐步构建：配置 → 模块 → 编排 → 前端 → 测试

### 4.2 Skill 来源探索

实验文档推荐了多个 Skill 资源渠道。在实际调研中发现：

| 推荐资源 | 实际情况 |
|---------|---------|
| `github.com/anthropics/skills` | 提供通用 `frontend-design`、`pdf`、`webapp-testing` 等官方 Skill |
| `skills.sh` / `skillsmp.com` | 收录 28万+ 社区 Skill，可搜索安装 |
| `claude-plugins.dev` | 提供 `rag-implementation` 等社区贡献的 RAG 工作流 Skill |
| `github.com/run-llama/llama_index` | LlamaIndex 源码仓库，不包含可直接使用的 Claude Code Skill 格式文件 |
| `github.com/langchain-ai/langchain` | LangChain 源码仓库，`CLAUDE.md` 为项目开发规范而非 RAG Skill |

下载到本地的 `LlamaIndex-Tutorials`（入门教程 notebook）和 `langchain`（monorepo 源码）均无法直接作为 Claude Code Skill 使用。社区中真正可用的 Skill 形态存在于 `skillsmp.com` 和 `claude-plugins.dev` 等平台。

### 4.3 Skill 体系设计

最终采用的 Skill 组合：**2 个社区 Skill + 1 个自定义 Skill**：

| 模块 | Skill 名称 | 来源 | 核心约束 |
|------|-----------|------|---------|
| PDF 解析 | `pdf-parser` | **自定义**（MySkills） | PyMuPDF 主引擎（禁止 pdfplumber）；页眉页脚清洗；EasyOCR 中文识别；过滤小图标 |
| RAG + 向量库 | `rag-implementation` | **社区**（claude-plugins） | Phase 1-8 完整 RAG 工作流：嵌入选择 → 向量库 Schema 设计 → 分块策略 → 检索实现 → LLM 集成 |
| 前端界面 | `frontend-design` | **社区**（anthropics/skills） | 生产级前端设计：独特排版、色彩主题、动效、避免"AI 生成感"的通用审美 |

![Skill体系Venn图](实验记录(图片)/Venn图.png)

自定义 Skill 与社区 Skill 的分工：
- **pdf-parser（自定义）**：编码阶段一 Issue #3（中文乱码）、#4（表格编码）、#6（噪声清洗）的经验。这些是中文金融 PDF 的特有问题，社区通用 Skill 不会覆盖
- **rag-implementation（社区）**：提供标准 RAG 架构框架，避免从零定义检索策略、向量库设计等通用逻辑
- **frontend-design（社区）**：提供前端设计方法论，输出"暗金金融终端"主题的 Streamlit 界面

### 4.4 Agent 任务拆解轨迹

Agent 加载 3 个 Skill 后，将总任务拆解为 5 个构建阶段：

```text
总任务: PDF智能问答系统（2个社区Skill + 1个自定义Skill）
│
├── [自定义: pdf-parser] ────→ Stage 2: pdf_parser.py
├── [社区: rag-implementation] → Stage 3-4: embedding + vector_store + build_kb + LLM
│     ├── Phase 2: Embedding Selection  → embedding_engine.py
│     ├── Phase 3: Vector DB Setup       → vector_store.py
│     ├── Phase 4: Chunking Strategy     → build_kb.py
│     └── Phase 6: LLM Integration       → app.py (Prompt部分)
└── [社区: frontend-design] ──→ Stage 5: app.py (UI部分)
      └── 设计方向: "暗金金融终端" — 深色背景 + 暖金点缀 + 编辑级排版

构建顺序:
  Stage 1 → 项目骨架 config.py
  Stage 2 → PDF解析模块 pdf_parser.py（自定义 skill）
  Stage 3 → 向量化引擎 + 向量存储 embedding_engine.py + vector_store.py（社区 skill）
  Stage 4 → 知识库构建器 build_kb.py（社区 skill Phase 4+5）
  Stage 5 → Streamlit前端 + 测试 app.py + test_questions.py（社区 skill Phase 6 + 社区 skill 设计）
```

关键差异：Agent 在社区 `rag-implementation` 的 Phase 1-8 工作流框架下，自动按标准 RAG 架构组织代码，同时在 `frontend-design` 指引下输出了定制化 UI 设计。

### 4.7 遇到的问题与解决

阶段二共遇到 **2个问题**，均为环境配置问题，无核心逻辑 bug：

---

**问题一：Starlette 版本不兼容**

- **现象**：`streamlit run ./app.py` 报 `ImportError: cannot import name 'DEFAULT_EXCLUDED_CONTENT_TYPES'`
- **原因**：虚拟环境中 `starlette 1.1.0` 与 `streamlit 1.57.0` 不兼容，Starlette 1.x 移除了部分旧 API
- **解决**：`pip install "starlette<1.0"` 降级至 0.52.1

---

**问题二：Milvus Lite AllocTimestamp 警告**

- **现象**：构建知识库时控制台报 `NotImplementedError: Method not implemented!`（AllocTimestamp）
- **原因**：Milvus Lite 本地文件模式使用 gRPC 桩，`AllocTimestamp` 方法在嵌入式模式下不需要，属于无害的兼容性警告
- **解决**：无需处理，不影响文本/图片集合创建、向量插入和搜索。67 段文本 + 59 张图片均正常入库

### 5.4 对比分析

**1. 模块化 vs 集中式**

阶段一将所有类内嵌在单个 `build_kb.py` 中（540行，4个类），修改 PDF 解析逻辑需要在一个大文件中定位代码。阶段二拆分为独立模块，每个模块职责单一。分离关注点后总代码量从 ~1100 行降到 ~950 行（约减少 14%）。

**2. 知识传递：社区 Skill + 自定义 Skill**

这是两个阶段最根本的差异。阶段一的 Agent 对中文 PDF 的编码问题、Milvus 的 released 机制、OCR 分数偏高等问题没有先验知识，只能通过试错来发现。

阶段二采用分层 Skill 策略：
- **社区 Skill**（`rag-implementation`、`frontend-design`）提供通用框架和方法论——RAG 的标准 Phase 流程、前端设计原则
- **自定义 Skill**（`pdf-parser`）承载项目特有的经验——中文编码兼容性、页眉页脚清洗、EasyOCR 配置

实验发现：社区 Skill 生态中对中文金融 PDF 解析这一细分领域尚无成熟 Skill（`skillsmp.com` 上的 `knowledge-ingestion-patterns` 侧重英文文档），因此保留了一个自定义 Skill 填补缺口。结果是核心逻辑 bug 从 5 个降为 0 个。

**3. 设计质量提升**

阶段二的 `frontend-design` 社区 Skill 提供了前端设计方法论，而非具体代码模板。Agent 据此输出了"暗金金融终端"主题——深色背景、暖金点缀、Playfair Display 标题字体、JetBrains Mono 等宽字体、25 个 CSS 变量、按钮悬停过渡动画。与阶段一通用的 Streamlit 默认样式形成显著差异。

**4. 社区 Skill 的可发现性问题**

实验文档推荐的 LlamaIndex 和 LangChain 仓库并非 Claude Code Skill 格式。`skillsmp.com` 和 `claude-plugins.dev` 等平台才是真正的社区 Skill 来源。当前社区生态中，通用框架 Skill（如 RAG 工作流、前端设计）已相对成熟，但针对特定场景（如中文 PDF 解析）的细粒度 Skill 仍然稀缺，需要自定义补充。

## 六、心得体会

### 6.1 单提示词 vs 社区Skill协同

单提示词一次性生成的优点是"快"——一条提示词就能拿到完整系统。但缺点是 Agent 缺乏领域知识约束，容易在细节上踩坑，调试成本高（阶段一 7 个问题，5 个核心逻辑 bug）。

引入社区 Skill 后，调试问题降至 2 个，且均为环境配置问题（Starlette 版本、Milvus 警告），核心逻辑 bug 为 0 个。关键差异不在 Skill 数量，而在 Skill 质量——社区 `rag-implementation` 提供了经过验证的标准 RAG Phase 流程，Agent 无需从零摸索检索策略和向量库 Schema。

但社区 Skill 并非万能。中文金融 PDF 的编码问题、页眉页脚清洗等细粒度经验，当前社区生态中尚无现成 Skill 覆盖，仍需自定义 `pdf-parser` 来承载。**社区 Skill 解决通用架构问题，自定义 Skill 解决领域特定问题**——两者分工而非替代。

### 6.2 复杂系统的多组件协同

RAG 系统涉及 PDF 解析、向量化、数据库、LLM 调用、前端五个组件的协同。核心经验：

- **组件边界越清晰，调试越容易**。阶段一所有组件混在单文件中，定位问题时需要在 540 行代码中追溯调用链。阶段二职责拆分后，问题定位直接从文件名就能判断
- **先让每个组件独立可验证，再编排**。`pdf_parser.py` 可以单独运行验证文本提取是否正确，`vector_store.py` 可以单独测试搜索功能，不必每次都跑全流程

### 6.3 社区 Skill 生态的现状

本次实验对社区 Skill 生态的探索发现：

- **通用框架类 Skill 已相对成熟**：`rag-implementation`（RAG 工作流）、`frontend-design`（前端设计）等可直接使用，效果良好
- **细粒度领域 Skill 仍然稀缺**：`skillsmp.com` 上 28 万+ Skill 中，针对"中文金融 PDF OCR + PyMuPDF 编码兼容"这一具体场景的 Skill 几乎不存在
- **Skill 格式不等于源代码仓库**：实验文档推荐的 `llama_index` 和 `langchain` 仓库是项目源码，不是 Claude Code 可加载的 Skill。真正可用的 Skill 在 `skillsmp.com`、`claude-plugins.dev` 等聚合平台
- **自定义 Skill 仍是必要补充**：社区 Skill 提供框架，项目特有的经验仍需自定义 Skill 承载

### 6.4 对 Agent 辅助开发的思考

本次实验证明了 **"社区 Skill + 自定义 Skill"混合策略**的有效性：

- 不是 Agent 不够聪明，而是它缺乏项目的"经验记忆"。阶段一的问题并非 Agent 能力不足，而是它对"这个特定中文 PDF 应该用什么工具解析"、"Milvus Lite 有什么坑"没有先验知识
- 社区 Skill 将通用最佳实践传递给 Agent（如 RAG 的 Phase 1-8 标准流程），避免从零定义架构
- 自定义 Skill 将项目特有的踩坑经验持久化（如"禁止 pdfplumber"、"必须 load_collection"），让经验可跨项目复用
- 数据隔离（每个版本独立的 `data/` 目录）让多版本并行开发和对比成为可能
