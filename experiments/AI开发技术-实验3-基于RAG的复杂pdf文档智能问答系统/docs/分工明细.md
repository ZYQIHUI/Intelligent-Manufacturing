## 阶段一（PromptVersion）— 成员C 独立负责

**代码量**：2个核心文件，~1100行，集中式架构

| 文件 | 行数 | 内容 |
|------|------|------|
| `build_kb.py` | 540行 | 内嵌4个类的单文件：PDF解析、向量化、Milvus存储、分块编排 |
| `app.py` | 560行 | Streamlit前端、检索、LLM调用、配置面板 |
| `test_questions.py` | — | 4道样本题测试 |
| `prompt.txt` | — | 系统提示词模板 |

**答辩重点**：
- 7个调试问题中挑3个关键问题讲解（中文乱码→换PyMuPDF、整页检索→分块、OCR虚高→均衡采样）
- 初始方案 vs 最终方案的6项变更（见报告3.5节对比表）
- 集中式架构的优缺点

## 阶段二（SkillVersion）— 成员D + 成员E 分工

**代码量**：8个文件，~950行，模块化架构

### 成员D — RAG后端管线

| 模块 | 对应Skill | 内容 |
|------|----------|------|
| `config.py` | rag-implementation | 全局参数：分块、检索、模型、路径 |
| `pdf_parser.py` | 自定义 pdf-parser | PyMuPDF文本提取 + EasyOCR图片识别 + 噪声清洗 |
| `embedding_engine.py` | rag-implementation Phase 2 | BGE模型加载、批量向量化 |
| `vector_store.py` | rag-implementation Phase 3+5 | Milvus双集合设计、插入、COSINE搜索、统计 |
| `build_kb.py` | rag-implementation Phase 4+5 | 知识库构建编排（解析→分块→向量化→存储） |

**答辩重点**：
- 自定义Skill `pdf-parser` 如何承载阶段一的踩坑经验（禁止pdfplumber、页眉页脚清洗规则）
- 社区Skill `rag-implementation` 的Phase流程如何指导架构设计
- 双集合设计 + 分块策略（chunk=512, overlap=50）与阶段一的演进关系

### 成员E — 前端界面 + 检索生成

| 模块 | 对应Skill | 内容 |
|------|----------|------|
| `app.py` 检索部分 | rag-implementation Phase 5+6 | 跨集合均衡检索、Prompt模板、DeepSeek调用 |
| `app.py` UI部分 | frontend-design | "暗金金融终端"设计系统（25个CSS变量、字体、动效） |
| `app.py` 交互功能 | — | 侧边栏配置、API/DB状态检测、PDF上传、对话管理 |
| `test_questions.py` | — | 4道样本题 + 2道扩展题、检索命中验证 |

**答辩重点**：
- `frontend-design` Skill 的设计方法论如何落地（色彩体系、字体选择、组件定制）
- 均衡检索策略（文本8条 + 图片4条，文本优先，不按分数混排）
- 两版本UI对比演示（默认Streamlit vs 暗金金融终端）
- 扩展题测试结果（市场整体表现、机构调研个股补充了样本题的覆盖面）

## 分工总览

```
阶段一 (PromptVersion)  →  成员C  [独立]
阶段二 (SkillVersion)   →  成员D  [后端: PDF解析→向量化→入库]
                        →  成员E  [前端: 检索→生成→UI界面]
```

**答辩串讲逻辑**：
1. 成员C讲阶段一的集中式方案和7个调试问题
2. 成员D讲阶段二如何用社区Skill + 自定义Skill重构后端
3. 成员E讲前端设计升级和最终检索效果
4. 汇报人总结对比（7→2调试、5→0核心bug、1100→950行）
